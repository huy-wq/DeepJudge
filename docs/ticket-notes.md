## #2 单份评分闭环（2026-10-26，commit `1c94c0b`）

### 一、流程与测试

| 问题 | 现象与原因 | 处理 | 教训 |
| --- | --- | --- | --- |
| 测试缝与工单不匹配 | spec 定的是「HTTP 层一条缝」，但 #2 交付物是命令行，此时还没有 API。按约定写不出测试 | 退到 CLI + 流水线这一层作为临时缝，并在提交说明里写明 | 缝要随交付物走。票 #5 之后必须回到 HTTP 缝，否则测试会被固定在内部结构上 |
| TDD 循环被跳过 | 第 4 轮「加固测试」一次全绿——因为第 3 轮已经把所有防御都写了 | 如实记录，没有伪造红灯 | 第 3 轮写多了。一个红绿循环只该满足当前那一条断言，「顺手防御」会让测试失去发现问题的能力 |
| 工具装不上 | 环境无外网，`pytest`、`fastapi` 都无法安装 | 测试改用标准库 `unittest`；核心模块不依赖任何第三方包 | 这个限制反而是好事：它强制核心逻辑与框架解耦。后续引入 FastAPI 时，`core/` 仍应保持零依赖 |

### 二、设计与文档

| 问题 | 现象与原因 | 处理 | 教训 |
| --- | --- | --- | --- |
| 依赖方向违规 | `pipeline.py` 放在 `core/`，却 import 了 `providers.base`。文档规定 `core/*` 只能依赖标准库 | 把 `pipeline.py` 移到 `app/`（编排层） | 目录不是装饰。文档写了依赖规则，就得有地方检查它——现在只能靠人工审查发现 |
| 命名漂移 | 代码里是 `Provider`、`GradingResult`，文档里是 `GradingProvider`、`SampleJudgement` | 全部改成文档名 | 文档先写、代码后写时，命名会自然漂移。开工前扫一遍文档里的标识符，比事后改名便宜 |
| 文档已定义、代码还没有 | 文档 §4.3 的 `ItemJudgement` 有 `span`、`grounded`，实现里没有 | 不提前补，留给 #3 证据接地 | 这是**正确**的顺序：字段跟着行为走，不跟着文档走。但要在票里写明「本票不含」 |
| 没有检查文档与实现一致的手段 | 上面两条不一致，都是 review 阶段才发现的 | 暂无自动化手段 | 短期靠 review；若再出现两次，值得加一个"文档标识符 vs 代码标识符"的检查脚本 |

### 三、实现细节

| 问题 | 现象与原因 | 处理 | 教训 |
| --- | --- | --- | --- |
| 结构错误没能「一次报全」 | 缺字段时直接 `raise`，跳过了语义校验；验收要求"一次报出全部问题" | 改成收集式解析：先收集结构问题，再跑语义校验，最后一起抛 | 「一次报全」不是 `validate()` 一个函数的事，解析阶段也会提前退出 |
| CLI 遇到坏文件直接 traceback | 评分标准 JSON 语法错误、文件不存在都没捕获 | `load_file` 包装成 `RubricError`，CLI 统一退出码 2 | 命令行工具的第一条纪律：用户输入错误不该打印调用栈 |
| 扣分项缺失的语义没定义 | 模型漏掉扣分项时静默当作"未命中"，而采分点漏项却报错 | 明确定义为"扣分项是命中才出现的负面证据，缺失即未触发"，并加测试固定 | 同一份输出里，两类字段的缺失语义不同，必须显式写下来，否则下一个人会当成 bug 改掉 |
| 代码围栏与「严格解析」的张力 | 模型常把 JSON 包在 ```json 里；剥掉围栏算不算"宽容" | 剥围栏保留，但错误码区分 `INVALID_JSON` / `NOT_OBJECT` | 宽进严出：入口容忍常见格式噪音，出口必须结构化、可判别 |
| 没有真实 Provider | LLM API 未定，CLI 只能吃预置的模型输出 | 接口 + 离线假实现先行，命令行用 `--response` 传入 | 未定的外部依赖应该被挤到最边缘。#2 的交付因此完全可离线验证 |
