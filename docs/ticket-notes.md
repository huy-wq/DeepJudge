## #2 单份评分闭环（2026-10-26，commit `1c94c0b`）

### 一、流程与测试

| 问题 | 现象与原因 | 处理 | 教训 |
| --- | --- | --- | --- |
| 测试缝与工单不匹配 | spec 定的是「HTTP 层一条缝」，但 #2 交付物是命令行，此时还没有 API。按约定写不出测试 | 退到 CLI + 流水线这一层作为临时缝，并在提交说明里写明 | 缝要随交付物走。票 #5 之后必须回到 HTTP 缝，否则测试会被固定在内部结构上 |

### 二、设计与文档

| 问题 | 现象与原因 | 处理 | 教训 |
| --- | --- | --- | --- |
| 依赖方向违规 | `pipeline.py` 放在 `core/`，却 import 了 `providers.base`。文档规定 `core/*` 只能依赖标准库 | 把 `pipeline.py` 移到 `app/`（编排层） | 目录不是装饰。文档写了依赖规则，就得有地方检查它——现在只能靠人工审查发现 |
| 命名漂移 | 代码里是 `Provider`、`GradingResult`，文档里是 `GradingProvider`、`SampleJudgement` | 全部改成文档名 | 文档先写、代码后写时，命名会自然漂移。开工前扫一遍文档里的标识符，比事后改名便宜 |
| 文档已定义、代码还没有 | 文档 §4.3 的 `ItemJudgement` 有 `span`、`grounded`，实现里没有 | 不提前补，留给 #3 证据接地 | 这是**正确**的顺序：字段跟着行为走，不跟着文档走。但要在票里写明「本票不含」 |

### 三、实现细节

| 问题 | 现象与原因 | 处理 | 教训 |
| --- | --- | --- | --- |
| 结构错误没能「一次报全」 | 缺字段时直接 `raise`，跳过了语义校验；验收要求"一次报出全部问题" | 改成收集式解析：先收集结构问题，再跑语义校验，最后一起抛 | 「一次报全」不是 `validate()` 一个函数的事，解析阶段也会提前退出 |
| CLI 遇到坏文件直接 traceback | 评分标准 JSON 语法错误、文件不存在都没捕获 | `load_file` 包装成 `RubricError`，CLI 统一退出码 2 | 命令行工具的第一条纪律：用户输入错误不该打印调用栈 |
| 扣分项缺失的语义没定义 | 模型漏掉扣分项时静默当作"未命中"，而采分点漏项却报错 | 明确定义为"扣分项是命中才出现的负面证据，缺失即未触发"，并加测试固定 | 同一份输出里，两类字段的缺失语义不同，必须显式写下来，否则下一个人会当成 bug 改掉 |
| 代码围栏与「严格解析」的张力 | 模型常把 JSON 包在 ```json 里；剥掉围栏算不算"宽容" | 剥围栏保留，但错误码区分 `INVALID_JSON` / `NOT_OBJECT` | 宽进严出：入口容忍常见格式噪音，出口必须结构化、可判别 |
| 没有真实 Provider | LLM API 未定，CLI 只能吃预置的模型输出 | 接口 + 离线假实现先行，命令行用 `--response` 传入 | 未定的外部依赖应该被挤到最边缘。#2 的交付因此完全可离线验证 |

## #3 证据接地（2026-10-26）

### 一、审查发现的设计缺陷

| 问题 | 现象与原因 | 处理 | 教训 |
| --- | --- | --- | --- |
| 容错匹配会"拼凑命中" | 最初把全篇所有匹配块的长度加起来算相似度。证据「客户端三次握手」在原文里是分散的，却被判命中，span 覆盖整卷 93 个字符 | 改为**以最长匹配块为中心的局部窗口**，只在窗口内评估 | 相似度算法必须约束"局部性"。全局块拼接等于允许任意重组，假阳性会非常多 |
| 短证据一字之差就失败 | 阈值按比例（0.9）算：`ACK=2` 与原文 `ACK=1` 只差一字，比例 0.8 < 0.9，被判不命中 | 改为**允许错误数**：`max(1, 长度 × (1 − 阈值))`，短证据至少容忍 1 个字符 | 比例阈值对短文本没有意义。阈值要按"允许犯几个错"来定，而不是百分比 |
| 接地率分母失义 | 未命中的判定记 `grounded=True`，也计入分母。模型全部判未命中时，接地率 100% | 只统计**声称命中**的判定 | 指标要先想清楚"分母是谁"。把"没说的话"算成"说对了"，指标就失去意义 |
| `hit` 承担了两种含义 | 未接地时把 `hit` 置 False，用于计分；但审计上"模型声称过命中"这一事实丢了 | `hit` 保留声称，未接地只把 `level` 置 0；扣分项用 `hit and grounded` 判定是否生效 | 一个布尔不要同时表示"声称"和"采信"。分开之后，复核界面才能解释"模型说命中但证据找不到" |

### 二、规范与一致性问题

| 问题 | 现象与原因 | 处理 | 教训 |
| --- | --- | --- | --- |
| 文档承诺 LCS，实现是 difflib 局部窗口 | 架构 §2 写"子串 → LCS 容错"，实现用的是序列匹配块 | 改文档，让它描述实际算法；不为迁就文档去写一个更差的实现 | 文档先写时用近似描述；实现定型后必须回头把文档改准，否则文档会变成假承诺 |
| `UNGROUNDED` 只是布尔，没有可呈现的标记 | 评审要求"标 UNGROUNDED"，代码里只有 `grounded=False` | 增加 `ungrounded_ids()`，CLI 报告输出 `ungrounded` 列表 | 设计里出现的专有名词，应该在输出里有对应字段，否则复核界面无从展示 |
| 扣分项没有 span | 只给采分点算了位置，扣分项算完即弃 | `DeductionJudgement` 补 `span`，CLI 一并输出 | 同类对象要对称。只做一半，下一张票还得回来补 |
| 两段同构循环 | items 与 deductions 的接地逻辑几乎一样 | 抽 `_ground()`，并给两个判定类型加 `mark_grounded` / `mark_ungrounded` | 重复的不只是循环，还有"未接地时该改哪些字段"这条规则；方法化之后规则只有一个出处 |
| `apply_grounding` 直改五个字段 | Feature Envy：接地模块越权操作判定对象 | 把状态变更收进判定对象的方法 | 谁的数据谁负责。副作用集中的地方，最容易泄漏业务规则 |
| 测试文件结构 | `unittest.main()` 夹在两个类之间，直接运行只跑第一个类 | 重写文件，守卫放末尾 | 这种错误不会让 CI 失败（discover 照跑），只会在手工运行时静默少跑测试——更危险 |

### 遗留

- 接地率尚未接入路由（#8）与持久化（#5）。当前只在单次结果与 CLI 报告中可见。
- 文档 §4.4 把 `grounding_rate` 列在聚合层；目前先在单次结果上有实现，聚合时取加权平均即可。

### 未决

- 无新增。上一张票的「最高等级分值是否必须等于权重」仍待拍板。

## #4 多采样与路由（2026-10-26）

### 一、审查发现的缺陷

| 问题 | 现象与原因 | 处理 | 教训 |
| --- | --- | --- | --- |
| 置信度漏了接地率因子 | 架构 §2.1 写的是"置信度 = 1 − 离散度，**再乘 grounding rate 惩罚项**"，实现只做了前半句。三次全部未接地时置信度仍是 1.0 | 改为 `confidence = (1 − 离散度) × 接地率` | 文档里写成公式的东西，必须逐项对照代码；漏一个因子，指标会给出完全相反的结论 |
| 扣分项分歧不计入离散度 | 只有扣分项在三次采样间翻转时，离散度为 0、置信度 1.0，只能靠极差兜底 | 扣分项按扣分幅度折算进离散度，整体截断到 1 | 聚合要覆盖"所有会变的东西"。只统计采分点，扣分项的分歧就漏网了 |
| 报告里聚合值与单份证据混用 | `level` 取中位数，`evidence`/`grounded` 取某一份采样，可能出现"等级 1.0 但 grounded=false" | 证据改取"等级等于中位数且已接地"的那份；`hit` 取任意、`grounded` 取全部 | 报告里混用两种来源，用户看到的就是自相矛盾的数据；要么全聚合，要么标注来源 |
| `--samples 0` 直接 traceback | 只在 `evaluate` 里抛 `ValueError`，CLI 没接住 | `argparse` 层校验并报错退出 | 参数校验放在入口，别指望下游函数替你挡住非法输入 |

### 二、有意保留的判断（不是缺陷）

| 争议点 | 说明 |
| --- | --- |
| 满分答案被转人工 | 验收写"三次一致即自动通过"，但边界带规则会让 10.0 转人工。二者是**并列条件**：一致是必要条件，不是充分条件。满分是后果最重的判定，复核一次是合理代价 |
| 偶数次采样取下中位数 | 平均会产生非法等级（0 与 1 平均成 0.5，而某点可能只有 0/1 两档）。取下中位数偏保守，已在文档写明 |
| 及格线取 60% | 来自架构 §2.2 的边界带定义，属于可配置策略（`RoutePolicy.pass_ratio`） |
| `risk` 公式 | `极差 + (1−置信度)×满分 + 1`，是排序用的启发式，没有理论依据；只影响复核队列顺序，不影响结论 |

### 遗留

- 路由阈值未用真实数据校准（等有标注集再做，见路线图 T6.2）。
- 未接地率与置信度的乘积关系尚无实验支撑，属设计判断。

### 未决

- 无新增。

### 三、规范审查补充

| 问题 | 现象与原因 | 处理 | 教训 |
| --- | --- | --- | --- |
| 测试守卫又放错了 | `test_cli.py` 与 `test_aggregate.py` 新加的测试类放在 `unittest.main()` 之后。当前规范命令 `python3 -m unittest` 不受影响，但一旦有人直接运行脚本就会静默少跑 | 守卫统一移到文件末尾 | **同一个错犯了第二次**（#3 已记录）。这类问题不会让 CI 失败，只有手工执行时才暴露；测试文件的入口格式应该一次定死 |
| 路由阈值没有文档出处 | `pass_ratio=0.6`、`full_marks_margin` 只存在于代码与测试，文档没写 | 在 §2.2 补上四项信号与默认阈值 | 「文档是唯一设计真源」意味着每个魔法数字都要能指回某一段文字，否则下一个人不知道能不能改 |
| `decide()` 的 `rubric` 形参未使用 | 从旧签名残留，`max_score` 已经从 aggregate 取 | 删除该形参，调用方同步 | 参数一旦不用就删掉；留着会让人以为函数还依赖 rubric |
| 测试断言内部调用次数 | `provider.calls == 5` 断言的是实现细节 | 改为断言 `len(result.samples) == 5` | 断言"做了什么"而不是"调用了几次"，换实现时才不会误报 |
| 离线多采样会产生假置信度 | `--response` 同一份输出被重复采样，置信度必然 1.0 | CLI 在离线且 `--samples > 1` 时向 stderr 打提示 | 指标在不适用的场景下要主动声明，而不是给出一个看起来合理的数字 |

### 五、遗留的坏味道（记录下来，暂不处理）

- `build_report` 负责挑选"代表采样"并组装展示字段，逻辑偏重；如果继续变复杂，应拆到独立的展示模块。
- `risk` 公式是量纲混加的启发式，只在同批次内可比，没有理论依据。
- `route` 用 `Literal["auto", "human"]` 约束，但仍缺统一的错误码/状态枚举。

## #5 持久化（2026-10-26）

### 一、环境上的两件事（决定了这一票能验到什么程度）

| 情况 | 现象 | 处理 |
| --- | --- | --- |
| PyPI 突然通了 | `#3` 时 `pypi.org` 不通，`#3`/`#4` 才全程标准库；这次 `pymysql`、`sqlalchemy`、`alembic` 都装上了 | 存储层用 SQLAlchemy 2.0 Core + Alembic + PyMySQL，与 `pyproject.toml` 早已声明的依赖一致 |
| 本机没有 MySQL，也没有 sudo | `apt` 有 `mysql-server` 候选包，但装不了；镜像站的 MySQL 镜像反复在大层上 `EOF` | 单测跑内存 SQLite；MySQL 的字符集/方言验证写成**默认跳过**的真库用例，命令留在 README 与测试文件顶部 |

**这一票的诚实结论：MySQL 的建表 DDL 已经离线渲染并逐条看过（`CHARSET=utf8mb4`、`LONGTEXT`、`DOUBLE`、`JSON` 都在），
但"中文与 emoji 真能存进 MySQL"这一条，本机没有跑成。** 需要你在能起库的机器上跑一次
`tests.test_store_mysql` 才算真正闭环。

### 二、审查发现的缺陷

| 问题 | 现象与原因 | 处理 | 教训 |
| --- | --- | --- | --- |
| 浮点会变成 `Decimal` | MySQL 的 `DOUBLE` 默认 `asdecimal=True`，查询回来是 `Decimal('8.0')`，与领域对象的 `float` 不相等 | 统一 `mysql.DOUBLE(asdecimal=False)`，并在迁移里显式写死 | "字段无损"不是"列都在"，而是"读回来的 Python 对象相等"；类型漂移是最隐蔽的丢数据 |
| 同一个字段存两处版本号 | 原表设计里 `grading_runs.rubric_version` 与 `rubrics.version` 各存一份 | 改成 `rubric_id` 外键指向不可变快照，版本号 join 出来 | 两处冗余必然漂移；能用一个外键表达的，不要用两个整数表达 |
| 扣分项硬塞进采分点的列 | `item_results` 原本只有 `rubric_item_id` 与 `level`，而扣分项没有等级 | 加 `kind`（`item`/`deduction`），`level` 允许为 `NULL` | 用一个字段装两种含义，迟早会造出"扣分项等级 0"这种假数据 |
| 迁移与模型会悄悄漂移 | `tables.py` 是代码真源、`migrations/` 是部署真源，两边都能改 | 加测试真的跑 `upgrade head` / `downgrade base`，再把表、列、可空性、索引、唯一约束、外键逐项对照 | "测试库建得起来"不等于"生产库建得起来"；两个真源之间必须有机器强制对齐 |
| 迁移里的默认值带了 SQLite 方言 | autogenerate 反射出 `sa.text('(CURRENT_TIMESTAMP)')`，是 SQLite 的写法 | 手工校正为 `CURRENT_TIMESTAMP`，并在迁移里写注释说明为何改 | 自动生成的迁移一定要读一遍；生成器的输入是什么方言，输出就带什么方言的痕迹 |

### 三、有意保留的判断（不是缺陷）

| 争议点 | 说明 |
| --- | --- |
| 写入是一个大事务 | 标准快照、答卷、N 次运行、逐条判定、聚合结果全进或全不进。半份数据比没有数据更危险——复核的人会以为那就是当时的结论 |
| `questions` 复用而不更新 | 题干改了不覆盖旧行，靠 rubric 版本表达变化。题目本身的内容变更不在本课题范围内 |
| 标准按 `checksum` 去重 | 内容相同就复用最新一版快照，避免每次评分都堆一版；内容变（含回滚到旧内容）就追加新版本，版本号始终单调 |
| `--save` 不负责建表 | CLI 只写入，建表只能走 `alembic upgrade head`。让程序自动 `create_all` 会掩盖"生产库少了迁移"这类事故 |
| 真库用例默认跳过 | 没有 `DEEPJUDGE_TEST_MYSQL_URL` 就 skip，而不是失败。默认套件必须能在没数据库的机器上一条命令跑完 |

### 四、规范审查抓出来的问题

| 问题 | 现象与原因 | 处理 | 教训 |
| --- | --- | --- | --- |
| 迁移与模型不一致 | 注释写着"浮点显式 `asdecimal=False`"，生成的列却是 `mysql.DOUBLE()` | 迁移里显式写 `mysql.DOUBLE(asdecimal=False)` | 自动生成的迁移里，注释和代码不是一件事；改了模型要回头核对生成物 |
| 存储层反向依赖编排层 | `store/repository.py` import 了 `pipeline.Evaluation`，而 §3 的依赖表只允许它依赖 core、providers | 依赖表补上这一条并说明理由（`Evaluation` 就是"一次评分的产出"这个类型） | 文档写"允许依赖"时，要想到读取方需要的返回类型；与其让代码委屈，不如把规则写准 |
| 迁移脚本绕过公开出口 | `migrations/env.py` 直接 import `app.store.tables`，与 `__init__.py` 里"不要直接 import tables"自相矛盾 | `app.store` 显式导出 `metadata`，env.py 走公开出口 | 自己定的边界自己先破，别人就没有理由遵守 |
| 每条运行都重查一次标准 | `_load_sample` 内部再查 rubric、再 `from_dict`，与 `load_evaluation` 重复 | 由调用方把 rubric 传下去 | 一个查询在外层已经做过，就别在内层再写一遍；"字段无损"的代价不该是 N 倍查询 |
| NULL 被静默补成 0 | `level ... else 0.0`、`score ... else 0.0` | 遇到 NULL 直接报错 | 这正是 §4.4 里"NULL 是没校准，不是校准为 0"的同一条原则：**补 0 是最难发现的造假** |
| `psql` 子命令跑的是 mysql 客户端 | 复制粘贴留下的名字 | 改名 `shell` | 工具的名字写错，比工具本身不好用更误导人 |
| `create_schema()` 与"建表只走迁移"并存 | 测试需要快速建表，但它和迁移并列成公开 API | 保留并在 docstring 里写明"只给单测与本地一次性脚本"，生产与 CI 走 alembic | 便利方法和正式流程并存时，必须把边界写在调用者看得到的地方 |

### 五、需求审查抓出来的问题

| 问题 | 现象与原因 | 处理 | 教训 |
| --- | --- | --- | --- |
| 运行元信息写而不读 | `model` / `params` / `tokens` / `latency` / `error` 存进了 `grading_runs`，但 `load_evaluation` 只返回领域对象，这些列永远读不回来 | 加 `RunRecord`，`StoredEvaluation` 同时带答卷元信息（脱敏号、truncated、规范化文本）与每次运行的元信息 | "字段无损"要按**每一列**验，不是"领域对象相等"就算完；审计要用的字段恰恰都不在领域对象里 |

## #10 标准生成（2026-10-27）

### 一、这一票真正难的不是"调模型"

把一段口述变成 JSON，模型基本能做。难的是**模型做错时系统不能跟着错**，所以四件事都是服务端的活：

| 要求 | 实现位置 | 为什么不能交给模型 |
| --- | --- | --- |
| 满分/题干/题号以教师为准 | `rubric_gen._with_server_owned_fields` | 模型把满分改成 5 分，整套标准就废了；同名字段一律丢弃重填 |
| 权重不足只报差额、不补点 | `rubric.WEIGHT_SUM` 的文案 | 自动补点 = 替教师编采分点，直接违反"不得新增" |
| 校验清单分两类 | `RubricIssue.blocking` | 只给中文句子的话，前端只能靠匹配中文来分类——文案一改就崩 |
| 不合法重试一次 | `generate_rubric` 的循环 | 重试时必须把错误原样回灌，否则模型只会重复同一个错 |

### 二、发现并修掉的问题

| 问题 | 现象与原因 | 处理 | 教训 |
| --- | --- | --- | --- |
| 校验结果只有中文句子 | `RubricError.problems` 是 `list[str]`，调用方要区分"阻断/提示"只能去匹配"权重合计"这类字面量 | 引入 `RubricIssue(code, message, blocking)`；`problems` 保留为派生属性，旧调用方零改动 | 给人看的文案与给程序用的分类必须是两个字段；把语义塞进字符串，迟早靠正则救场 |
| `rubric_gen` 放错了层 | 初版写在 `core/`，却要 `import providers` 才能调模型，违反"core 只依赖标准库" | 移到 `app/rubric_gen.py`（编排层，与 `pipeline.py` 同级），架构 §3 同步 | 和 `#5` 的 `store→pipeline` 同一类错误：写之前先看依赖表 |
| JSON 取包逻辑重复 | 评分流水线里有一份剥围栏 + 解析，生成也要用，但 core 不能 import pipeline | 抽成 `core/json_extract.py`（`PayloadError` + `extract_payload`）；pipeline 在外层转成 `GradingError` | 两处都要用的东西，谁在下游谁上移；不要让"层"变成复制粘贴的借口 |
| 摘要完全依赖模型 | 模型忘写 `summary` 时，三视图缺一个 | 加 `_compose_summary` 兜底，用采分点与权重拼一句话 | 三视图里凡是模型产出的那一份，都要有确定性兜底，否则一个字段的缺失能让整份结果不可用 |

### 三、有意保留的判断

| 争议点 | 说明 |
| --- | --- |
| "不得新增采分点"靠提示词而非代码 | 没有可靠办法把自由文本和采分点做集合比对。代码能做的是**不替模型补点**，以及重试时明确禁止补点；剩下的靠三视图让教师看 |
| `VAGUE_CRITERION` 用固定词表 | "论述充分/理解到位"这类词是可枚举的常见糊弄语。词表必然不全，所以它只做**提示**，绝不拦保存 |
| `DUPLICATE_DESC` 只查完全相同 | 近似重复需要语义相似度，成本与误报都不划算；宁可漏报也不误伤 |
| 重试上限写死 2 次（原调用 + 1 次） | 与验收"自动重试一次"一致。更多次只会放大成本，不改变"模型就是不会"的结局 |
| 生成用哪个档位的模型留给调用方 | 架构说生成用"强档模型"，但模型名是部署参数；函数只接受 `GradingProvider`，选谁由入口决定 |

### 五、遗留

- **生成侧还没有 HTTP 接口**（REST 属 #7/#13）。目前入口是 `backend/scripts/gen_rubric.py`，
  离线 `--response` 与在线 `--live` 两条路都能跑。
- `summary` 没有长度约束，模型可能写很长；展示层截断即可，不入库。
- 教师原话（§5.6 要求留档）目前只在调用方手里，落库要等 `#11 标准保存与迭代`。

### 五、审查抓出来的问题（都已修）

| 问题 | 现象与原因 | 处理 | 教训 |
| --- | --- | --- | --- |
| 差额被"去噪"逻辑吃掉 | 结构错误时过滤 `WEIGHT_SUM`。模型漏掉一个采分点的 `weight` 时，清单只剩"缺少必填字段"，"还差 3 分"完全消失——而这正是教师最需要的数字 | 去掉过滤，一律带上差额 | 去噪的前提是"那条信息没用"。差额不是噪音，**它是唯一的行动指引** |
| 差额先 `round` 再判方向 | 满分 10、权重合计 9.996 时，`round(0.004, 2) = 0`，输出"超出 0 分"，方向和数值都错了 | 先用原始差值定方向，格式化时才 `:g` | 舍入是展示问题，不能掺进判断逻辑；先判后格式 |
| 模型能改评分行为 | `_with_server_owned_fields` 透传了模型给的 `rules`，采分点里的 `must_hit`/`acceptable` 也照收 | 采分点只保留 `id/desc/weight/levels`，扣分项只保留 `id/desc/penalty/cap`，`rules` 恒为空 | "服务端拥有最终决定权"要**逐字段落实**，写一句注释不算 |
| 生成与评分共用模型变量 | 只读 `DEEPSEEK_MODEL`，与架构 §5.2"强档模型分开配置"不符 | `DeepSeekConfig.from_env(model_env=...)`；生成读 `DEEPSEEK_GEN_MODEL`，留空退回前者 | 文档写了"分开配置"，代码就得有那个变量；否则配置项等于不存在 |
| 在线生成失败直接 traceback | `EXIT_PROVIDER=4` 只覆盖了构造配置那一步，`complete` 抛的 `ProviderError` 没人接 | 在 `generate_rubric` 外层捕获 `ProviderError`，按可重试/不可重试分流 | 入口要接住**整条链路**的失败，不是只接第一步 |
| 校验清单有两条产路 | `from_dict` 算完 `validate` 把仅提示项丢掉，`rubric_gen` 只好再算一遍 | 引入 `parse() -> ParsedRubric(rubric, issues)` 作为唯一引擎；`from_dict` 变成它的一层包装 | 同一份清单只能有一个生产者；"算完扔掉再算一次"迟早两处说法不一致 |
| `attempts` 参数与注释自相矛盾 | 注释写"上限写死 2 次"，函数却允许传 1 或 5 | 删掉参数，用 `MAX_ATTEMPTS` | 可配置不等于更好：调用方不该回答"该试几次"这种由验收决定的问题 |

### 六、交付前补的两处

| 补什么 | 为什么 | 结果 |
| --- | --- | --- |
| `GeneratedRubric.views()` | 验收要求"同时返回三份数据"，但把 `summary` / `preview_rows` / `issues` 分开给，调用方很容易只拼摘要和预览、**漏掉最该看的校验清单** | 一次返回 `rubric + summary + preview + checklist + attempts`，HTTP 层可以直接拿它当响应体 |
| 评分 CLI 现在会打印"仅提示"项 | 分类做了却没人用，等于没分类。标准里出现"满分不可达"这类问题时，`app.cli` 原本一声不响 | 载入标准后把 `validate()` 的仅提示项打到 stderr，仍照常评分（退出码不变） |

顺带给生成脚本加了一句离线提示：同一份预置输出喂给重试必然得到同样结论，
免得把"离线重试没用"误读成"重试机制坏了"（与 `#4` 的离线多采样提示同一类问题）。

## #6 认证（2026-10-27）

### 一、把"签名 cookie"改成了服务端会话

架构 §5.8 最初写的是"下发签名 cookie"。验收里有一条"退出后原凭据立即不可用"，
而签名只能证明"这个 cookie 是我发的"，不能证明"它还没被撤销"：

```
退出 → 服务端不再认这个 sid，但无状态令牌仍然自洽 → 有人留着旧 cookie 照样进
```

所以实现改成**随机会话 id + 服务端登记表**：登录登记一行、退出删掉、过期自动清。
测试里专门有一条"退出后重放退出前抓到的 cookie 必须 401"，就是为了钉住这个差别。

代价写进了架构 §5.8：会话存在内存里，重启全失效、多 worker 不共享。升级路径是换共享存储，
`AdminAuth` 的接口不用动。

### 二、发现并修掉的问题

| 问题 | 现象与原因 | 处理 | 教训 |
| --- | --- | --- | --- |
| 启动失败抛错了类型 | 口令缺失时 `AdminAuth` 抛 `ValueError`，但这是"配置没准备好"，不是"参数写错了" | `create_app` 先自己检查环境变量并抛 `RuntimeError`；`AdminAuth` 的 `ValueError` 留给"直接构造时传空" | 同样是"没有口令"，启动期与构造期的语义不同，报错类型要能区分场景 |
| 路由与依赖分不开 | 首版把 `get_auth` / `require_admin` 和路由写在同一个文件里，还出现了 `HTTPException_401` 这种取巧的辅助函数 | 拆成 `api/deps.py`（判断）与 `api/routes.py`（读写 cookie），`require_admin` 直接返回 `Session`，路由里不再二次 `verify` | 依赖就是"这次请求是不是管理员"这一个问题；把它和路由混在一起，`HTTPException` 就得四处拼装 |

### 三、有意保留的判断

| 争议点 | 说明 |
| --- | --- |
| 退出接口不要求登录 | 幂等：会话已过期时前端也能正常退出，不卡在 401 上 |
| 过期与未登录返回同一句话 | 都是"未登录或会话已失效"。区分它们等于告诉攻击者"这个 sid 曾经存在" |
| 没有登录失败限速 | 单用户、内网/本地演示，优先级低；已记入架构 §5.8 的代价表 |
| cookie 的 `Secure` 用环境变量控制 | 本地 http 演示必须关掉，否则浏览器根本不收 cookie；公网必须打开，架构已写明 |
| 用工厂函数而不是模块级 `app` | 模块级 `app` 会让"没配口令"在 import 期爆炸，测试收集与脚本引用一起遭殃；工厂函数把失败点挪到启动那一刻 |

### 四、遗留

- `ADMIN_PASSWORD` 目前只做"非空"校验，没有强度要求。演示口令短一点方便，公网部署前应加最小长度。
- 会话登记表在内存里，`active_sessions()` 只给测试与排查用，没有暴露成接口。
- 没有 CSRF token：靠 `SameSite=Lax` 挡住跨站表单提交。若将来出现跨站 POST 需求，需要补 token。

### 五、未决

- 是否需要"登出所有设备"（清空登记表）的运维入口。单用户场景大概率不需要。
- 多 worker 部署时的会话共享方案（Redis / `admin_sessions` 表）等部署形态定了再说（架构 §9「部署」仍待定）。

## #7 答卷导入（2026-10-27）

### 一、这一票真正的风险是"隐私从缝里漏出去"

验收写的是"不保存真实姓名学号"，但实现要求比这句话更细：**任何返回给前端或写进日志的地方都不能有学号**。
第一版把坏行原文（`raw`）一起返回，理由是"教师好定位"——可坏行恰恰是不知道哪一列是学号的行，
一旦回显，学号就原样进了响应体。改成只回 `行号 + 原因`，用行号定位（Excel 里第几行）。

有一条测试专门守这个：`test_broken_rows_never_echo_the_original_line`。

### 二、发现并修掉的问题

| 问题 | 现象与原因 | 处理 | 教训 |
| --- | --- | --- | --- |
| 坏行会回显原文 | 坏行清单带 `raw`，而坏行无法判断哪列是学号 | `ProblemRow` 只留 `line` 与 `reason` | "不存学号"要管住**每一条出站路径**，不只是数据库 |
| 表头判定太宽松 | 只看"有一个单元格像表头"就跳过整行，学生答案恰好写"答案"两个字时会被当表头吃掉 | 改成**所有**非空单元格都是表头词才算表头 | 启发式规则要往"误伤数据"那一侧多想一步 |
| 列角色只看第一行，却不校验后续行 | 首行定宽度后，后面列数不同的行被按错位解析 | 宽度定为基准，不一致的行直接进坏行清单 | 格式约定要"先定契约再逐行对"，不是每行各自猜 |
| 表头里认不出学号列 | `_header_index` 只记题号与答案，`rows_with_student_id` 永远报 0 | 增加 `STUDENT_HEADERS` 只为统计，内容读入即丢 | 统计口径错了不会报错，只会让人以为"这批数据没学号" |
| 多题 CSV 的查重只查了一个题号 | 预览按上游传的 `question_code` 查重，混题文件里其他题的行永远不标重复 | 按**每行自己的题号**分组查重 | 一个请求里有多份数据时，聚合口径要跟着数据走，不能跟着参数走 |

### 三、审查抓出来的问题（都已修）

| 问题 | 现象与原因 | 处理 | 教训 |
| --- | --- | --- | --- |
| 跨题号误标重复 | 预览把各题的内容指纹并成一个集合再判断。Q-01 已有"三次握手"时，Q-02 里同样的文字也被标重复 | 查重按 `(题号, 指纹)` **成对**判断，store 提供 `find_duplicates(pairs)` | 查重键是两个字段，就不能只拿其中一个去比对 |
| 预览不查批内重复 | 同一文件里出现两遍时，预览说"无重复"，入库却跳过一行 | 预览同时算库内与批内；只把**第二次及以后**的出现标重复 | 预览与入库必须用同一套判断，否则"确认过"是假的 |
| 预览与入库对未知题号的结论相反 | 预览给 `exists:false` 只是提示，入库却整批 404 | 预览也直接 `ok:false` 并说明先保存标准 | 同一个文件在两处的结论必须一致，否则教师会以为能导 |
| 422 会回显请求内容 | FastAPI 默认 422 带 `input`，而导入接口的 `input` 就是整段 CSV——里面有学号 | 接管 `RequestValidationError`，只回字段与原因 | 隐私要求要覆盖**框架默认行为**，不只是自己写的分支 |
| 表头有空列时角色错位 | `_header_index` 先过滤空单元格再用下标，位置整体前移，可能把学号列当成答案列 | 判定用过滤后的值，**下标一律用原始位置** | "过滤后重建数组"是下标 bug 的经典来源 |
| 测试基建重复且描述失真 | `upgrade_database` 复制了 `test_migrations` 的 Config/env 处理；`support.py` 的 docstring 还说"测试不走迁移" | 抽出 `database_url` 上下文与 `upgrade_database`，两个测试文件共用；docstring 按实情改写 | 测试基建的注释也要跟着改，否则下一个人按它做决定 |

### 四、有意保留的判断

| 争议点 | 说明 |
| --- | --- |
| 查重口径 = 规范化后相同 | 全角/半角、多空格视为重复。宁可多标一次重复（教师可再确认），也不要放过真重复 |
| 重复只是"跳过"，不报错 | 教师重复导入同一份文件是很常见的操作，报错会打断流程 |
| 题号必须已存在 | 答卷属于某道题，题目由保存评分标准时创建。导入前提示"先保存这份标准" |
| 预览返回答案全文 | 那是教师自己的数据，且学号已丢；不给全文就没法核对解析对不对 |
| 入库与预览共用同一份原文重解析 | 不接收客户端回传的行：收下就等于把"预览的准确性"交给前端 |

### 五、遗留

- **没有导入批次表**：撤销"整批导入"目前无处下手（只能按 `answer_id` 删）。验收只要求"取消导入不产生数据"，已满足；
  真要做"撤销这一批"，需要 `import_batches` 表，等有需求再加。
- 单文件上限未设：`text` 直接进 JSON body，超大 CSV 会先撞 FastAPI 的请求体上限。
- 没有"导出模板"：教师得自己拼 CSV 表头。`data/samples/answers.csv` 给了一份样例。
- `content_hash` 为空串的历史行查不出重复（迁移不回填）。真要用时需写一个回填脚本，架构 §4.4 已注明。

### 六、未决

- 学号列如果实际是"姓名"，同样按学号处理（丢弃）。若某天需要"同名不同人"的区分，要改口径。
- 题号格式未校验（`Q-01` 只是惯例，`Q1`、`q-01` 都能存）。是否需要规范化待定。

## #8 批量评分任务（2026-10-27）

### 一、并发是这一票唯一真正的难点

任务跑在线程里，写入同一个库。三件事必须成立：**同一份答卷不能被评两次**、
**一份失败不能拖垮整批**、**进程重启后不能留下永远"进行中"的任务**。

前两条靠代码，第三条靠启动时的一次清理（`mark_interrupted_tasks`）。

### 二、发现并修掉的问题

| 问题 | 现象与原因 | 处理 | 教训 |
| --- | --- | --- | --- |
| **同一份答卷被评两次** | `claim_next_item` 先 SELECT 再 UPDATE，两个 worker 可能同时读到同一行 pending，于是都评一遍。表现是"聚合结果比任务项多"，测试间歇失败 | 改成 CAS 循环：带 `status='pending'` 条件更新，`rowcount != 1` 就重新取 | 并发下的"读-改-写"必须有一个原子步骤；先读后写永远有窗口 |
| SQLite 不查外键，测不出数据损坏 | 插了一条指向不存在答卷的 `task_item`，SQLite 默默接受；只有列表里"少了一份"才露出 | 连接时 `PRAGMA foreign_keys=ON`；并在 `create_task` 里先校验答卷属于该题 | 测试库越像生产库越好，否则"测试过了"是假的 |
| 内存库跑不了多线程 | `StaticPool` 让所有线程共用一个连接，事务互相踩 | 测试改用临时文件库；`from_url` 对 SQLite 文件库加 `timeout` 容忍写锁 | 基础设施的默认值决定了你能测什么 |
| 任务总显示"进行中" | 进程崩溃后 running 状态没人清理 | 启动时 `mark_interrupted_tasks()` 把 running → interrupted，item → failed（可重试） | 只要有状态机，就要有"上电自检" |
| 失败项无法单独重试 | 只实现了"全部失败重来" | `reset_failed_items(task_id, answer_ids=...)`，接口支持传子集 | 验收写"可单独重试"，就得真能只挑一份 |
| 测试收尾时库被删、线程还在写 | `TemporaryDirectory` 清理早于 daemon 线程结束，打出 disk I/O error | 加 `TaskRunner.wait_all()`，测试 tearDown 先等任务停 | 后台线程的生命周期必须有人负责收尾 |
| 请求问题被当成 500 | 选了不属于该题的答卷时 `create_task` 抛 `ValueError`，路由没接，浏览器收到 500 | 路由里把 `ValueError` 转成 400 并带上原因 | 「代码出错」与「请求不对」必须分开，否则前端只能显示"服务器错误" |

### 三、审查抓出来的问题（都已修）

| 问题 | 现象与原因 | 处理 | 教训 |
| --- | --- | --- | --- |
| **执行器崩溃后任务永远卡住** | `_run` 只有 `try/finally` 没有 `except`：`claim` 或写库抛异常时线程静默猝死，`wait()` 仍返回 True，任务停在 `running`，而 `/retry` 又会因"任务还在跑"拒绝重试——那份任务彻底废了 | `except` 里把任务标成 `interrupted` 并记 `error`，再尽力重置失败项；迁移里新增任务级 `error` 列 | "异常会被上层处理"是假设，不是事实；线程里的 finally 只保证收尾，不保证**留下痕迹** |
| 中断后计数不重算 | `mark_interrupted_tasks` 只改任务状态，`failed` 仍是 0，而每一份其实都失败了 | 中断后调用 `_recount` 按 item 真实状态重算 | 有派生计数的地方，状态一变就要重算 |
| 子集重试把整体 `failed` 清零 | 只重试 1 份时，其余失败项还在，但任务显示 0 个失败 | 重置后重算，而不是写死 0 | 局部操作不要动全局计数 |
| 计数用"读出来再写回" | 两个 worker 同时完成时互相覆盖（MySQL 默认隔离级别下更明显） | 改成 `done = done + 1` 增量，且只在状态真的变化时加 | 并发下的计数器只能做原子增量 |
| 快照指向错的行 | 任务改了标准后，`save_evaluation_for_answer` 按内容又插入一版，导致 `aggregate.rubric_id != task.rubric_id` | 增加 `rubric_id` 参数，任务直接把快照 ID 传下去 | "按内容找版本"适合手动评分，不适合"已经钉死快照"的任务 |
| 请求问题被当成 500 | 选了不属于该题的答卷时 `create_task` 抛 `ValueError`，路由没接 | 路由里转成 400 并带上原因 | 「代码出错」与「请求不对」必须分开 |
| 重复答卷 id 撞唯一约束 | 前端勾选重复时传两次同一个 id，`total` 偏大且插入失败 | 建任务前按顺序去重 | 外部输入先去重，再算计数 |
| "待复核"只能前端自己拼 | `task_items` 没有这个状态，接口也不给，前端得同时看 `status` 与 `route` | 接口加派生字段 `state`（`graded` / `needs_review` / `failed` / `pending` / `running`），数据库仍不存 | 验收要的是"教师能看到三态"，不是"数据库里存三态" |

### 四、有意保留的判断

| 争议点 | 说明 |
| --- | --- |
| 进程内线程池，不上队列 | 单用户、单机演示。多 worker 部署时换成共享队列，`TaskRunner` 接口不变（架构 §9 已记） |
| 有失败项也算任务 `done` | 状态在每一项上；把任务本身标成 failed 会掩盖"大部分评完了"的事实 |
| "待复核"不单独存状态 | 它就是聚合结果的 `route`，存两份必然出现自相矛盾 |
| provider 用工厂 | 假 provider 的响应游标、真实客户端的连接状态都不该跨答卷复用 |
| 一次只跑一个任务线程 | 同一任务重复 `start` 会被忽略；多个任务各自一个线程，靠线程池上限兜住并发 |

### 五、遗留

- 任务没有"取消"入口：跑起来只能等它结束（或重启进程）。单用户场景优先级低。
- 进度靠轮询（前端每 1–2 秒查一次），没有 SSE/WebSocket。任务量小时够用。
- 任务级并发 (`GRADING_CONCURRENCY`) 只在本机生效，多进程部署时每进程各算各的。

### 六、未决

- 是否需要"按班级/批次"给任务分组与命名。现在只有 `task_id` 与题号。
- 失败重试是否要限制次数（避免教师反复点、反复烧钱）。目前不限。

## #9 复核与改分（2026-10-27）

### 一、这一票的核心是"两份证据"

复核最容易做成"把最终分覆盖上去"。那样做，事后没人能回答两个问题：模型当时给了多少？老师改了几分、为什么改？
所以这一票坚持：**`aggregated_results.raw_score` 与 `reviews.final_score` 并存**，复核只追加一行，不改写原分。

第二件事是**定稿是一次性的**。"已定稿的答卷不因标准后续修改而变化"这条验收，光靠"标准快照不可变"（#5 已有）
不够——还得保证复核记录指向的是**某一次**结论，而且那次结论没有被后来的重评取代。

第三件事是**定稿之后不能再评**。只锁"某一次结论"不够：同一份答卷可以再评一次、再定稿一次，
于是出现两条互不隶属的"最终"记录。定稿必须锁住**答卷**。

### 二、发现并修掉的问题（实现期）

| 问题 | 现象与原因 | 处理 | 教训 |
| --- | --- | --- | --- |
| 队列会列出已被重评取代的旧结论 | 队列只按 `route='human'` 过滤，同一份答卷评两次就出现两行；教师可能对旧分数定稿 | 队列只列每份答卷**最新**的聚合结果；接口再挡一次，给旧结论定稿返回 409 `RESULT_SUPERSEDED` | "待办列表"必须定义在**当前有效**的数据上，否则列表本身就是错的 |
| "批量通过高置信结果"口径不清 | 直接按 `confidence` 排序会混进边界分、未接地等仍需人看的结果 | 只接受 `route='auto'`：那正是系统判定"无需人工"的集合；转人工的必须逐份看 | 把"系统认为不用看"和"数值看起来高"分开，别让教师无意中绕过路由 |
| 队列的 `total` 一开始是"本页条数" | `limit` 截断时前端会以为队列只有 100 条 | store 增加 `count_results`，与 `list_results` 共用同一套筛选条件 | 列表接口里 `total` 的含义必须是"总数"，不是"这次返回了几条" |
| MySQL 上删索引会撞外键 | 迁移先 `drop ix_reviews_aggregate` 再建唯一索引；`aggregated_result_id` 上有外键，MySQL 不允许删掉唯一支撑它的索引 | 先建唯一索引、再删旧索引；降级反之 | SQLite 测不出 MySQL 的索引约束，涉及外键列的 DDL 顺序要按文档推理 |
| 并发重复提交 | "先查有没有复核记录、再插入"中间有窗口 | `uq_reviews_aggregate` 唯一索引兜底；`IntegrityError` 转 409 | 能用数据库约束表达的不变量，不要只靠应用层判断 |
| 复核请求的错误形状不统一 | 缺意见、分数越界、批量混入待复核项、重复定稿，各自散在路由里 | 领域异常 `ReviewRejected` / `ResultFinalized` / `ResultSuperseded` / `ResultNotFound`，统一在 `api/errors.py` 映射 400/409/404 | 前端只需要认一种错误形状：`{detail, code}` |

### 三、审查抓出来的问题（都已修）

| 问题 | 现象与原因 | 处理 | 教训 |
| --- | --- | --- | --- |
| 迁移测试没验"唯一" | `describe_database` 只比索引**名字**，把唯一索引改成普通索引也能通过 | 索引比对带上 `unique` 标志 | "结构对齐"必须包含约束强度，不只是名字 |
| NaN 绕过分数区间校验 | `NaN < 0` 与 `NaN > max` 都是 False；SQLite 把 NaN 存成 NULL，撞 NOT NULL 后又落进 `except IntegrityError`，报成"已定稿" | `math.isfinite` 先挡；补一条 400 用例 | 区间判断挡不住 NaN；错误信息必须与事实一致 |
| 详情 404 有两种形状 | 详情抛裸 `HTTPException`，复核走领域异常 `RESULT_NOT_FOUND` | 统一抛 `ResultNotFound`，由同一处映射 | 同一个条件不要有两种响应形状 |
| 等级缺失时补 0 | `levels.get(item.id, 0.0)` 会静默造出"评了 0 分" | 改成下标取值，数据坏了直接炸 | 补 0 是最难发现的造假（#5 的教训） |
| 批量通过漏捕冲突 | 并发重复批量通过撞唯一索引 → 500 | 与单份一致捕成 409，整批回滚 | 同一条不变量，两条写入路径都要兜 |
| 定稿后仍可重评 | `create_task` 不看复核记录，重评后同一答卷出现两条互不隶属的"最终"记录 | `create_task` 与 `save_evaluation_for_answer` 双重拒绝；"已定稿"列表不再套"最新一次"过滤 | "定稿"要锁住**答卷**，只锁住某一次结论不够 |
| 详情看不出"已过期" | 拿着旧链接打开是 200，页面没有任何提示 | 详情返回 `current` / `superseded_by` | 能打开不等于还是当前结论 |
| 任务页对定稿无感知 | `task_item_views` 只选原分，定稿后仍显示 `needs_review` + 旧分；被重评取代的任务项也仍显示"待复核"，但复核接口会 409 | 任务项带 `final_score`，派生态加 `finalized` 与 `superseded` | 派生状态要在**所有**视图里一致，不能只修队列 |
| 复核与重评的并发窗口 | 单份复核、批量通过、重评都是"先查后插"，可以同时通过检查：一边定了稿，另一边插了更新的聚合结果 | 三处都对同一聚合行 `FOR UPDATE`，MySQL 下串行化（SQLite 忽略，但单写者） | 检查-插入的窗口要么加锁，要么明确承认它；补锁时要把**所有**写入路径数一遍 |
| 队列跨题按 risk 混排 | 与 §2.2"只在同一批次内可比"直接矛盾 | 先按题号分组、组内按 risk 排序 | 不可比的数字不要放在一起排序，哪怕看起来更好排 |
| 两个 rows 函数重复 | 逐采样的证据/偏移映射写了两遍 | 抽 `_sample_rows` | 同一形状出现两次，第三次就会漏改 |
| 测试夹具重复 | 两份新测试各抄一遍 `payload_with_levels` 与两档分歧样本 | 移进 `tests/fixtures.py` | 夹具也是代码，复制即漂移 |
| 文档行号漂移 | 新写的 §⑬ 引用的是加代码之前的行号 | 按最终代码重算 | 行号引用要放在最后一次改代码之后 |

### 四、有意保留的判断

| 争议点 | 说明 |
| --- | --- |
| 复核只追加，不改写原分 | 模型分与人工分是两份证据；覆盖掉就说不清"改了多少、为什么改" |
| 一份结果只定稿一次 | 定稿是结论，不是草稿。错误改分或重复点击都不该悄悄覆盖；更正需要未来的撤销/重开流程 |
| 改分必须写意见 | 没有理由的改分无法解释，也无法作为教师一致性的样本 |
| 批量通过整批一个事务 | 混进一份待复核结果就整批不落库，避免"通过了一半"这种说不清的状态 |
| `reviewer_id` 固定 `admin` | 系统只有一个共享口令，无法区分是谁操作的（架构 §5.8 已写明）。加名字只会得到无法验证的自报身份 |
| 队列按题号筛选，不按任务 | 任务只是"一次批量操作"，复核关心的是"这道题还有哪些没定稿" |
| 不复用 `cli.build_report` 的选证据逻辑 | CLI 报告与 HTTP 详情的字段形状不同，硬抽一个 presenter 会把命令行和接口层绑在一起 |
| `decision` 用字符串而非枚举 | pydantic `Literal` 挡在 HTTP 边界，store 再挡一次直接调用；为一个两值字段引入跨层枚举收益太小 |
| 过期任务项只标 `superseded`，不改指向最新聚合 | 任务保留了当时的 rubric 快照，把任务项指到另一个任务的聚合结果上会混两套标准 |
| 接口比 #1 的草案多了批量通过与分页参数 | 草案只写了队列与单份复核；"批量通过高置信结果"是 #9 的验收，`limit`/`offset`/`pending`/`question_code` 是队列可用所必需，已写进架构 §2.3 与 README |
| 详情返回答卷全文与参考答案 | 复核要按证据偏移在原文上高亮，也要对照参考答案判断判定对不对；复核人就是出题教师，接口在管理员会话之后 |

### 五、遗留

- 没有"撤销定稿/重新复核"入口。目前定稿后只能读，不能改；需要时再加状态与流程。
- 任务视图只有 `final_score`，没有复核意见、修改人与复核时间。要查看这些得走详情接口。
- 队列用 `limit` + `offset` 分页，`total` 给总数；没有游标分页，也没有"下一页"的稳定快照（复核中途有人定稿会让分页轻微错位）。
- 复核记录只保留"当前这一条"，没有"历次复核"列表。一次定稿的前提下没有第二条可列。
- MySQL 真库仍未验证（本机无 MySQL、Docker 拉取失败）；唯一索引、外键与 `FOR UPDATE` 的顺序只做了文档级推理，靠 SQLite 迁移测试守住结构对齐。

### 六、未决

- 定稿后需要更正怎么办：加一个 `reopen` 动作（把复核记录作废并允许再定稿），还是允许追加第二条复核记录、以最新为准？前者保住"定稿"语义，后者保住历史。
- 多人复核时如何记录真实身份：需要账号体系，`reviewer_id` 才有意义。
- 批量通过是否允许跨任务、跨题号选择。现在接口不限制，前端大概率会按任务筛选后再提交。
- 复核与重评的串行化在 SQLite 上只是"单写者"的副作用，没有真正的行锁；如果将来上多进程 + SQLite，需要重新评估。
- 队列现在按题号分组、组内按 `risk` 排；是否需要再按"任务"分组展示（同一题可能批改过多轮）待定。

## #11 标准保存与迭代（2026-10-27）

### 一、保存不是"写文件"，是"追加一个不能被改的版本"

这一票最容易做成"把 JSON 写进库、下次读出来"。那样做有两个后果：
已经建好的任务会随标准改动而"变味"（它指向的是同一行），"这个权重怎么来的"也无从追。
所以保存只有一条路：**内容变了就追加一版，旧版永不修改**；任务快照用外键指过去，
指标就永远读得到当时那份标准。

溯源随之落地为 `rubrics` 的两列：`source_text`（这一版依据的教师原话）与 `feedback`
（生成这一版时的意见）。它们跟着版本走，不是只记在题目上。

### 二、发现并修掉的问题（实现期）

| 问题 | 现象与原因 | 处理 | 教训 |
| --- | --- | --- | --- |
| 迭代会丢 `rules` | `_with_server_owned_fields` 固定写 `rules={}`，上一版确认过的开关被清空 | 迭代时把上一版的 `rules` 传进去；模型仍然改不动 | "服务端拥有字段"不等于"服务端给常量"，有些字段要**沿用** |
| 列表子查询自动关联 | `select(max(version)).where(question_id == questions.id)` 被 SQLAlchemy 自动关联掉，子查询没有 FROM，直接报错 | `.correlate(questions)` 固定关联范围 | 相关子查询要写清"关联谁、保留谁"，别指望默认行为 |
| 题干与满分出现两套真相 | 标准里存一份、`questions` 表里存一份；保存只创建不更新 | 保存路径用 `_upsert_question` 同步题干与满分；评分写入路径保持"只创建" | 同一事实存两处，就必须有一处负责同步 |
| 测试把 P1 映射到了下标 1 | 辅助函数用 `int(item_id[1:])` 当下标，整体错位，导致"改 P1"实际改了 P2，结构错误用例拿到 200 | 改成 `int(item_id[1:]) - 1` | 编号从 1 开始、下标从 0 开始，转换只写一次 |
| "生成失败"样本其实合法 | 构造的坏样本只有两个等级、分值也没越界，422 用例拿到 200 | 改成只有一个等级（`TOO_FEW_LEVELS`） | 造坏样本要先想清楚违反哪条规则，别假设"看起来怪"就一定非法 |
| 三处重复的 issue 序列化 | `views()`、错误处理、保存响应各拼一遍 `{code,message,blocking}` | `RubricIssue.to_dict()` 一处产出 | 同一个线上形状出现三次，改一次就会漏两处 |
| 测试夹具各写一份 | 两份新测试分别复制"改标准"的辅助函数与生成样本 | 统一进 `tests/fixtures.py`（`rubric_variant` / `generation_payload`） | 夹具也是代码，复制即漂移 |

### 三、审查抓出来的问题（都已修）

| 问题 | 现象与原因 | 处理 | 教训 |
| --- | --- | --- | --- |
| 首次保存没强制原话 | 架构 §5.6 写"首次保存要求带上原话"，实现里 `source_text` 只默认空串 | `POST`/`PUT` 都校验，缺了返回 400 `SOURCE_TEXT_REQUIRED` | 文档写了"要求"就必须在代码里真的拦，否则等于没写 |
| 复用版本丢掉新溯源 | 评分写入路径可能先建过同内容、但没带原话；之后保存返回 `reused`，溯源永远是空的 | 复用时**只补空值**，不覆盖已有原话/意见 | "内容没变"不等于"什么都不能写"；元数据可以补 |
| MySQL 不接受 TEXT 的裸默认值 | `server_default=""` 生成 `DEFAULT ''`，MySQL 8 只接受表达式 `DEFAULT ('')` | 模型与迁移都改成 `sa.text("('')")`；`alembic upgrade --sql` 离线验证 DDL | 迁移测试只比列名/nullable，方言细节要靠离线 DDL 或真库兜 |
| 迭代丢掉 `must_hit` / `acceptable` | `_with_server_owned_fields` 白名单只保留 `id/desc/weight/levels`，教师确认过的必答点与同义表述在改一句后消失 | 迭代时从上一版按 id 沿用这两个字段 | "模型不能决定"不等于"可以丢"；服务端要负责继承 |
| 版本来源不可追 | 迭代只回 `based_on`，保存时不记父版本；改旧版再存会得到一个看不出出处的更高版本号 | 新增 `parent_rubric_id`，`PUT` 保存时写入；自引用但不加外键 | 版本号说明先后，不说明来源，两件事要分开存 |
| 并发保存撞唯一约束 | 两次保存各算一次 `version+1`，后到的撞 `uq_rubrics_question_version` → 500 | 保存路径先锁题目行；撞车后若对方写的正是同一内容则复用，否则报错 | "读-改-写"要么加锁，要么能安全重试 |
| 列表/详情用位置下标取列 | `row[0]..row[8]`，改列就静默错位 | 改成 `.mappings()` 按名字取 | 列一多，下标就是一份没人维护的隐性契约 |
| 测试主入口不在文件末尾 | 新增的测试类写在 `if __name__ == "__main__"` 之后，直接运行时不会执行 | 把守卫移到文件最后 | 这个坑 #5 已经踩过一次，写在这里的目的是别再踩第三次 |
| 一个只做转发的小函数 | `_issue_payload(issue)` 只是 `return issue.to_dict()` | 直接调 `to_dict()` | 多一层转发不增加任何语义，只增加一个要同步的地方 |

### 四、有意保留的判断

| 争议点 | 说明 |
| --- | --- |
| 内容与最新版相同就复用那一行，不追加空版本 | 教师反复点保存很常见；版本号被"空改动"刷爆以后，任务快照的"第几版"就没意义了。代价：这一版的新 `feedback` 不落库（空着的 `source_text`/`feedback` 会补上，已有值不覆盖） |
| 首次保存强制填写教师原话 | 没有原话，日后没人能解释权重怎么来的（§5.6）。脚本和评分路径不受影响，它们不走这个接口 |
| `parent_rubric_id` 不加外键 | 标准只增不删，父版本不可能消失；SQLite 上加外键要重建整表，代价不值得 |
| 列表只给每道题的最新版 | 列表页的用途是"继续编辑/拿去评分"；历史版本按 `rubric_id` 直接打开 |
| 保存/详情响应里不再返回整型 `question_id` | `Rubric.question_id` 是题号字符串，再给一个整型同名字段，前端迟早拼错。题号用 `question_code`，数据库主键不对外 |
| 行内编辑只追加版本，不原地改 | 任务快照用外键指向某一版；原地改会让历史记录的标准跟着变（§5.5） |
| 保存时允许改题干与满分 | 标准里存着它们，改不了就只能重建题目。题目表跟着更新，旧任务不受影响（各自有快照） |
| 编辑时题号不可改 | 题号标识"这道题"；改题号等于把标准挪到另一道题，语义上不是"编辑" |
| 编辑没重发原话时沿用上一版 `source_text` | 只改一行描述不该把教师原话抹成空串 |
| 首次保存不强制 `source_text` | 脚本与旧路径保存的标准没有原话；强制会挡住它们。前端应当要求填写 |
| 生成草稿不落库 | 草稿可能被反复生成；落库会造出一堆没人确认过的版本。确认后才 `POST /api/rubrics` |
| 迭代从库里读上一版，不接收客户端回传 | 客户端回传的"上一版"可能是改了一半的草稿；以库里已确认的版本为基线才有据可查 |

### 五、遗留

- 没有草稿持久化：生成的草稿只活在响应里，刷新就丢。要"回到上一次生成"得重新调模型。
- 没有停用 / 删除标准。题目一旦创建就一直出现在列表里。
- 没有乐观并发控制：两个人同时编辑同一题，后保存的追加一版、不会覆盖前者的版本，但它的基线可能已经旧了。
- 列表不分页、不搜索；题量大了再说。
- 没有"回滚到某一版"的一键操作：可以打开旧版再保存成新版，但不会把列表指回旧版。
- MySQL 真库仍未验证（本机无 MySQL、Docker 拉取失败）；新列的默认值用离线 `alembic upgrade --sql` 确认是 MySQL 8 可接受的 `DEFAULT ('')`，结构对齐仍靠 SQLite 迁移测试。

### 六、未决

- 题号是否允许改名或迁移到另一道题。现在编辑时直接拒绝。
- 生成失败时是否把模型的原始输出回给前端排查。现在只在异常对象里，HTTP 只回 `issues`。
- 保存是否要记录操作者。与 #9 同因：单口令系统无法区分人。
- "内容相同就复用"时，新的 `feedback` 要不要单独存一条审计记录。现在只在原值为空时补写，非空则丢弃。
- 原话是否允许事后改写。现在只补空值、不覆盖；如果要支持"更正原话"，需要明确它算不算一次版本变更。

## #12 前端骨架（2026-10-28）

### 一、骨架的目标不是"好看"，是"不白屏、不迷路"

三件事先立住：**未登录去哪、刷新还算不算登录、接口挂了看到什么**。
页面本身只有登录、首页、404 三个，业务页留给 #13–#15。

登录态的关键选择：**前端不存 token，也不在 localStorage 里记"已登录"**。
唯一可信的是服务端会话；刷新时重放 `GET /api/auth/session`，带着 HttpOnly cookie 去问一次。
这样"退出后受保护页不可访问"不是靠前端删一个标记，而是服务端会话真的没了。

### 二、发现并修掉的问题（实现期）

| 问题 | 现象与原因 | 处理 | 教训 |
| --- | --- | --- | --- |
| 用 setup 抛错测 ErrorBoundary | 子组件 `setup` 抛错时 Vue 只报"缺少 render"，错误卡片不出现 | 改成在 `render()` 里抛错；并 `await nextTick()` 再断言 | 测兜底逻辑要制造"渲染期"错误，且给 Vue 一次 re-render 的机会 |
| jsdom 缺浏览器 API | Element Plus 部分组件依赖 `matchMedia` / `ResizeObserver`，测试环境没有 | `tests/setup.ts` 里补桩 | 组件库的测试环境不是浏览器，缺的 API 要显式补 |
| 依赖版本跨了大版本 | registry 上 `vue-router` 已是 5、TypeScript 7、Vite 8、Vitest 5 | 固定在成熟线：vue-router 4.6 / TS 5.9 / Vite 7 / Vitest 3 | 骨架阶段优先稳定与可查资料，不追最新大版本 |
| 全量引入 Element Plus | 构建产物 1MB，Vite 警告 chunk > 500KB | 骨架阶段接受；按需引入留给业务页稳定后再做 | 先跑通再优化，但要把代价写下来 |

### 三、审查抓出来的问题（都已修）

| 问题 | 现象与原因 | 处理 | 教训 |
| --- | --- | --- | --- |
| 401 只清状态、不跳转 | `markUnauthenticated` 清了本地态，但守卫只在"下一次导航"才跑；页面内请求 401 时教师停在一个空壳上 | 会话层加"401 导航回调"，路由模块注册 `replace` 到登录页；补"页面内 401 立刻回登录页"用例 | "清状态"和"离开当前页"是两件事，缺一件就等于没处理 |
| 登录错误弹两次 | `notifyError` 弹 toast，返回值又塞进 `el-alert`，同一句话出现两遍 | 登录失败只贴表单（用同一个 `errorMessage` 映射），全局 toast 留给页面级错误；测试断言不弹 toast | "统一文案"不等于"统一呈现"；表单错误贴字段旁边更合适 |
| ErrorBoundary 把导航也替换了 | 边界包在 `App.vue` 的 `router-view` 外，一旦渲染出错，顶栏与退出按钮一起消失，教师没法换页面 | 管理页用 `AdminLayout` 内层边界（`:key="route.fullPath"`，换页即重置），外层只兜登录页；测试断言错误卡出现时退出按钮仍在 | 兜底的范围要和"希望保留什么"对齐 |
| 懒加载失败是纯白屏 | chunk 404/断网发生在路由层，不经过组件生命周期，`ErrorBoundary` 与 `errorHandler` 都接不到 | `router.onError` → `notifyError` + replace 到 `/load-error`；该页面在主包里（不走懒加载） | 兜底页自己不能也依赖懒加载 |
| 会话响应缺字段时崩在 `undefined` | `request<T>` 只是类型断言；后端 200 给了空对象时 `info.authenticated` 抛 TypeError | `fetchSession` 校验 `authenticated` 是布尔，否则抛可读的 `BAD_SESSION_RESPONSE` | 类型断言在运行时什么也不保证；关键响应要验形状 |
| 守卫的错误被降级成通用文案 | `consumeSessionError()` 返回字符串，`errorMessage` 只认 `ApiError`/`Error`，于是显示"操作失败，请稍后重试" | `errorMessage` 增加字符串分支；补路由守卫用例 | 同一个"错误"在不同层可能是 `Error`、`ApiError` 或字符串，映射要覆盖 |
| 退出遇 401 仍停在管理端壳里 | client 已清状态，但 `AdminLayout` catch 只提示不导航 | 由 401 导航回调统一送回登录页；补"退出 401 也回登录页"用例 | 状态失效后的导航要集中处理，不能每个调用点各写一遍 |
| 401 接线是测试盲点 | client 测试换的是 spy handler，session 测试直接调 `markUnauthenticated`，删掉真实接线测试仍然全绿 | 增加"真实 `request` → 会话变 anonymous"用例 | 被替换掉的接缝本身也要有测试 |
| `meta.public` 没有类型 | 写错成 `pubic` 时 vue-tsc 发现不了，`/login` 会被当受保护页，形成重定向循环 | `declare module 'vue-router'` 扩展 `RouteMeta` | 路由元数据也是契约，值得让编译器检查 |
| 测试里真实 `ElMessage` 堆 DOM | 未捕获的错误提示会在 `document.body` 留下 toast 与定时器，污染后续用例 | `tests/setup.ts` 每个用例前装空 notifier；需要断言的用例自行替换 | 测试默认应安静，只有关心提示的用例才打开它 |
| `expiresAt` 写了没人读 | 会话模块存了过期时间，但页面从没用过 | 删除该字段，只保留服务端返回的 `expires_at`（类型层面） | 状态里每个字段都要有人读，否则就是在猜未来需求 |
| `messageOf` 与 `errorMessage` 重复 | 两处各写一遍 `ApiError`/兜底映射 | 合并到 `api/client.ts` 的 `errorMessage`，`feedback` 直接复用 | 同一映射分两处，文案迟早不一致 |

### 四、有意保留的判断

| 争议点 | 说明 |
| --- | --- |
| 不引入 Pinia | 现在只有一份会话状态，一个 `session.ts` 模块足够；多一层状态库只会多一套约定 |
| 不在 localStorage 存任何登录标记 | 标记可以被手工改成"已登录"，而服务端不认；以 `/api/auth/session` 为唯一真相 |
| 404 也要求登录 | 未登录时连"这个路径不存在"都不该泄露；未知路径先过守卫 |
| 退出失败时不假装退出 | 服务端会话可能还在，cookie 也还在；清本地态只会造成"看起来退了"的错觉 |
| 错误文案只有一个映射 | `ApiError` + `errorMessage`；登录失败贴表单，其余错误走全局提示，不重复弹同一句 |
| 401 立即回登录页 | 清状态与导航一起做；不依赖"下一次导航" |
| 两级 ErrorBoundary | 管理页内层（保留导航），登录页外层；内层随路由 remount 重置 |
| `/load-error` 放在主包 | 兜底页不能自己依赖懒加载 |
| ErrorBoundary 返回 `false` | 捕获后不再向上冒泡，导航栏还在，教师可以换页面而不是整页空白 |
| 开发期依赖 Vite 代理 | `/api` 同源才有 cookie；生产部署必须让静态站点与接口同源（反代），这一条写进架构 §5.9 |

### 五、遗留

- 生产部署未做：`npm run build` 的 `dist/` 需要静态服务器托管，并把 `/api` 反代到后端；没有 Nginx 配置或 FastAPI 静态托管方案。
- 只做了桌面宽度，没有移动端适配与无障碍检查。
- 全量引入 Element Plus，首屏包约 1MB（gzip 342KB）；按需引入/分包留待业务页稳定后处理。
- 没有浏览器端到端测试（Playwright）；当前用 Vitest + jsdom 测行为，不测真实浏览器行为（cookie、代理）。
- `/load-error` 只提供"刷新"，不会自动重试加载失败的 chunk。
- 没有错误上报与性能埋点。

### 六、未决

- 业务页多起来以后是否需要 Pinia；现在只有会话一份共享状态。
- 生产形态：Nginx 静态托管 + 反代，还是 FastAPI 直接托管 `dist/`？后者更简单，但会把前端发版绑在后端进程上。
- 前端权限粒度：现在只有"登录/未登录"，未来如果出现多角色，守卫要重做。

## #13 标准编辑页（2026-10-28）

### 一、校验规则只留一份

编辑页最容易走的路，是把后端的校验规则抄一份到前端：权重和、id 唯一、等级单调……
抄完能立刻"实时"，但从此有两份真源——前端说能存、后端拒绝，教师只会觉得系统在骗人。

所以这一票给后端加了一个**只读**接口 `POST /api/rubrics/validate`：编辑页每次改动（防抖 200ms）
把当前 JSON 发过去，服务端复用 `parse()` 返回同一套 `issues`。代价是每次编辑多一次请求，
换来"页面上的清单"与"保存时的判断"永远一致。`runValidation` 用一个自增序号丢弃过期响应，
避免慢请求覆盖新结果。

阻断项禁用保存（标准本身不成立）；提示项只要求勾"已知悉"（能算分，但可能不可靠，判断权在教师）。
提示的确认 key 是 `code|message`：内容一变，就得重新确认。

### 二、发现并修掉的问题（实现期）

| 问题 | 现象与原因 | 处理 | 教训 |
| --- | --- | --- | --- |
| 监听"合并后的标准"抓不到表格编辑 | `merged` 是 computed，展开 `rubric` 只读了顶层引用；改某个采分点的描述不会让它重算 | 改为 `watch([questionCode, stem, totalScore, referenceAnswer, rubric], {deep:true})` | 要监听"会变的叶子"，不要监听"重新拼出来的影子对象" |
| `data-test` 落在哪个元素上不统一 | `el-input` 把属性透传到内部 `<input>/<textarea>`；`el-input-number` 留在外层 `div` | 文本/数字输入直接选 `[data-test]`；数字输入的内部 input 再向下钻一层 | 组件库的属性透传规则要按组件确认，不能想当然 |
| 保存按钮在校验失败时仍可点 | 网络失败后 `runValidation` 返回 false，`save` 中止，但按钮状态没变 | 测试改为断言"没有发保存请求"，按钮保持可点以便重试 | "不可保存"和"这次没存"是两件事；重试比禁用更友好 |
| 列表页打开新版本要先造数据 | 测试点"打开"后编辑页会 `GET /api/rubrics/7`，mock 没给就被弹回列表 | mock 补上记录；导航断言改成 `vi.waitFor`（懒加载是异步的） | 路由跳转在测试里不是同步的，别用 `flushPromises` 一把梭 |
| 路由 `/rubrics/new` 与 `/rubrics/:id` 冲突 | 动态段会吞掉 `new` | 动态段用 `:id(\\d+)`，只匹配数字 | 静态路径与动态路径共存时，用约束把动态段收窄 |
| 保存按钮在"改动后、校验返回前"可点 | 防抖的 200ms 窗口里清单还是旧值；虽然保存会再校验一次，但按钮看起来已经能存 | 增加 `dirty`：一有改动立即置脏，`canSave` 要求"最新改动已校验完"；在途校验用序号作废 | "实时"不等于"立刻可信"；按钮状态要绑定"最新改动是否已校验" |
| 重新生成会继承上一次迭代的意见 | `pendingFeedback` 只在迭代时写入，点"生成草稿"没清掉，保存时会把旧意见记到新版本 | 生成成功后清空 `pendingFeedback` | 两个入口写同一份"本版说明"，换入口时要显式清 |

### 三、审查抓出来的问题（都已修）

| 问题 | 现象与原因 | 处理 | 教训 |
| --- | --- | --- | --- |
| 校验失败后页面仍说"没问题" | 503 时 `catch` 只弹了提示，`finally` 还是把 `dirty=false`，旧清单继续显示"没有发现问题"、保存也能点 | 增加 `validationError`：失败时保持未校验状态、禁用保存；清单面板改显示"校验失败，清单可能过期"；补用例 | "拿到了响应"与"拿到了**正确的**响应"不是一回事；失败态必须显式 |
| 生成 / 迭代 / 保存可以并发点 | 三个按钮互不禁用，迭代响应回来会覆盖保存中的状态 | 加 `busy`：任一操作进行中，其余按钮都禁用；处理函数也先判 `busy`；补迭代中保存不可用的用例 | 异步动作之间要有互斥，不能只靠"用户不会那么快" |
| 摘要不随编辑更新 | 摘要只在生成/载入时算一次，里面还写着每个点的权重；改了权重旁边数字还是旧的 | 用 `changeKey` 判定结构是否变过：没变用模型摘要，变了用按当前结构实时拼的句子；补用例 | 页面上的每个数字都要有"它为什么还是对的"的理由 |
| 重新打开时自动勾选全部提示 | `applyRecord` 把历史 warnings 直接标成已知悉，教师没看过也能存 | 重新打开时 `acknowledged` 置空，必须重新勾选；补用例 | "上次确认过"不等于"这一次确认过" |

| 测试盲点 | 没有"校验失败态 / 摘要更新 / 重开确认 / 并发互斥 / 离开确认"的用例 | 编辑器用例从 10 个补到 14 个 | 每个被修掉的 bug 都要有一条能复现它的用例 |

### 四、有意保留的判断

| 争议点 | 说明 |
| --- | --- |
| 校验走服务端，不在前端复制规则 | 两份规则迟早不一致；宁可多一次请求 |
| 提示项要勾"已知悉"才放行保存 | 与验收措辞一致；不是拦截，是让教师对"能算但不可靠"的地方表个态 |
| 预览表直接改嵌套字段 | 编辑页持有整份 `rubric`，表格只是它的视图；为每个单元格发事件只会把状态切碎 |
| 题号在打开已有标准时锁定 | 题号标识"这道题"；要换题就新建，而不是把一份标准挪走 |
| 只有勾选、没有"全部已知悉" | 一条条确认是这一屏存在的意义；批量确认会让提示变成噪音 |
| 扣分项只展示不可编辑 | 验收只要求改权重/描述/等级分值；编辑扣分项等有真实需求再加 |
| 重新打开已存版本时摘要由前端按采分点拼 | 模型摘要没有落库（它属于生成过程，不属于标准内容）；拼出来的句子与服务端兜底一致 |
| 校验失败时不沿用旧清单 | 旧清单可能已经与当前内容不符；宁可禁用保存、让教师重试，也不给一个"看起来通过"的假象 |
| 重新打开时提示必须重新确认 | 上次确认是上一次的判断；这次改没改、看不看，应该由这次的人决定 |
| 离开确认用 `window.confirm` | 最小实现，够用；自定义弹窗要引入额外状态与可访问性处理，留到有真实需求时 |
| 客户端 `composeSummary` 只是展示兜底 | 校验规则仍然只有服务端一份；这里拼的是"当前结构"的一句话，不参与任何判定 |
| 组件测试里的 validate 桩只验页面行为 | 规则真源由 `backend/tests/test_api_rubrics.py` 的 Validate 类守着；前端桩不会替它做判断 |
| 迭代入口与 `validate` 接口超出 #13 的验收 | 架构 §5.4 写了"迭代生成"、§5.3 要求实时校验清单；验收里的"校验清单实时更新"没有服务端接口就只能在前端抄规则，代价更大 |

### 五、遗留

- 不能增删采分点/等级/扣分项；只能改现有行。缺采分点需要重新生成或改原文再来。
- 没有"撤销/重做"，也没有草稿持久化：刷新页面会丢掉未保存的修改。
- 每次编辑都发一次校验请求（防抖 200ms）；离线时编辑不可用，也没有客户端兜底规则。
- 没有键盘操作与无障碍检查；表格里的输入框靠鼠标。
- 没有浏览器端到端测试；页面行为用 Vitest + jsdom 测，真实布局与滚动未自动验证。
- 离开确认只覆盖路由内导航；关标签页 / 刷新仍会丢掉未保存修改（没有 `beforeunload`）。

### 六、未决

- 是否允许增删采分点。允许的话，"保存"要从"整份提交"变成"逐行 CRUD"，校验也要能指出新增行。
- 模型摘要要不要落库，好让重新打开时看到生成时的原话，而不是前端拼的句子。
- "已知悉"要不要记为一条审计（谁在何时确认了哪条提示）。现在只存在于当前页面状态，重新打开要重勾。
- 是否加 `beforeunload` 提示关标签页/刷新的场景。
- 校验接口是否值得加一个轻量客户端副本做离线兜底；一旦加就是两份规则，需要自动对齐测试。

## #14 导入与任务页（2026-10-28）

### 一、一个页面，复用三个已有接口

这一票没有新增导入 / 任务接口：预览与入库用 #7 的两条路由，答卷列表用 `GET /api/answers`，
建任务 / 查进度 / 重试用 #8 的三条路由。页面只做三件事：把原文发给服务端、
把服务端派生好的状态显示出来、把任务号写进地址栏。

任务号进 URL（`/grading?task=12`）是这一页唯一的状态设计：刷新、前进后退、从复核页返回
都能接上同一个任务；代价是没有任务历史列表，换一个任务就找不到旧的。轮询只在
`pending` / `running` 时继续，`done` / `interrupted` 停止；失败时显式停下并给"继续刷新"，
不静默卡在"评分中"。

任务完成后的交接目标是 `/review`：这一票先落一个**只读**队列（按风险列出待复核结论与原因），
证据高亮、改分、批量通过与定稿留给 #15。这样"任务完成后可跳转"不是一条 404 链接。

### 二、实现期发现并修掉的问题

| 问题 | 现象与原因 | 处理 | 教训 |
| --- | --- | --- | --- |
| CSV 预览切题后答卷列表没跟着换 | `syncQuestionFromPreview` 直接改 `questionCode`，`el-select` 不会因此 emit `change`，`onQuestionChange` 不跑；第二步还挂着上一道题的答卷，发起评分被服务端 400 | 改题号后显式清空选择并 `loadAnswers()`；补"CSV 题号与当前选择不一致"用例 | 程序化改 v-model 不等于用户操作；依赖 `@change` 的副作用要自己再调一次 |
| 缺失题号的提示永远不显示 | 后端对"题号不存在"返回 `ok:false`，提示却写在 `v-if="preview.ok"` 里面 | 把提示移到 `ok` 分支之外；补用例 | 先确认错误分支的响应形状，再决定提示放在哪一层 |
| 一次轮询失败就永久停住 | `catch` 里只弹提示然后 `return`，没有重新排下一次，也没有手动入口 | 增加 `pollError`，任务卡片显示"自动刷新已停止"和"继续刷新"；补用例 | 自动刷新必须有失败态；"停住"比"报错"更难发现 |
| 重试后不轮询 | 重试接口在 `runner.start()` 后立刻读任务，回显状态可能还是 `interrupted`；`schedulePolling` 看到非 running 就不排 | 重试后 `schedulePolling(true)` 强制先读一次；补用例 | 不要用"刚启动的异步状态"决定还要不要继续观察 |
| 中断/未启动的任务重试不生效 | `/retry` 只在 `reset > 0` 时启动执行器。任务在执行器领取答卷之前中断时 `failed=0`，`reset=0`，任务永远停在 `interrupted` | 后端改为 `reset > 0` 或任务状态为 `interrupted`/`pending` 都启动；补两个 HTTP 用例（中断、未启动） | "没有失败项"不等于"没有活干"；状态判断要覆盖 pending 项 |
| 任务号写进 URL 时整页重置 | `ErrorBoundary` 的 key 是 `route.fullPath`，改查询参数会 remount，页面丢了刚建的任务 | key 改成 `route.path`（换页面仍会重置），并 watch `route.query.task` 处理返回/后退；补任务恢复用例 | 错误边界的 key 决定"什么算换了一页"；查询参数通常不该算 |
| 页面 900 行，三块职责混在一起 | 导入预览、答卷选择、任务进度全在一个 SFC 里 | 抽出 `components/grading/PreviewPanel.vue` 与 `TaskProgressPanel.vue`；页面剩约 700 行 | 不是所有东西都要拆组件，但"纯展示 + 明确 emits"的部分该拆 |
| 测试断言 Element Plus 内部类名 | 用 `.el-tabs__item` 切页签，违反"不断言组件库内部实现" | 给页签 label 加 `data-test`，测试只点 `[data-test="tab-paste"]` | 组件库升级会改类名；测试只认自己声明的锚点 |

| 队列测试只断言"请求带了题号" | 分组/排序是服务端行为，由 `test_reviews.py` 守；前端不复制排序规则 |

### 五、遗留

- 不支持 `.xlsx`；只收 UTF-8 的 CSV/文本（Excel 需另存为 CSV），2 MB 上限，GBK 文件会乱码。
- 某题答卷超过 500 份时列表只显示前 500（接口上限），但总数会显示；没有分页/翻页。
- 没有任务历史列表；关掉带 `?task=` 的链接后只能从复核队列或数据库找回旧任务。
- 任务页不展示逐条证据与采样分歧；这些在复核详情（#15）。
- 复核队列只读，不能定稿；也没有按题分组的表头，跨题时只能靠题号列区分。
- 没有浏览器端到端测试；文件选择、真实轮询与页面滚动只用 Vitest + jsdom 验证。
- 页面只做桌面宽度；没有移动端与无障碍检查。
- 上传后自动预览会立即发一次请求；大文件解析失败时仍保留文本供修改，但不支持"取消解析"。

### 六、未决

- 要不要加 `GET /api/tasks?question_code=` 任务列表，让教师能回到历史任务？加了就要想清楚"哪些任务该显示、过期任务怎么标"。
- `.xlsx` 是引入解析依赖（如 openpyxl）还是继续要求另存 CSV？前者方便教师，后者保持零依赖。
- 粘贴是否也要自动预览（防抖）？现在为了避开与"确认导入"的竞态，选择了手动。
- 复核队列要不要在 #15 里按题号分组，还是用筛选器只显示一道题？跨题 risk 不可比，分组更诚实。
- 任务页要不要提供"只重试某一批失败项"的多选？现在只有单份和全部失败项。

## #15 复核页（2026-10-28）

### 一、队列与详情拆开

队列只回答"先看哪几份"：待人工复核按风险排、自动通过单独一页签。详情只回答"这一分怎么来的"：
答卷原文、逐条判定、采样分歧、证据偏移，最后采纳原分或改分定稿。

详情用 `aggregate_id` 打开，不用 `answer_id`。同一份答卷可能被重评多次；按答卷号打开只能拿到
最新一次，旧链接就说不清当时看的是什么。按结论号打开，页面才能明确回答"这是不是当前成绩"
（`current` / `superseded_by`），旧结论也不会被误定稿（服务端 409）。

高亮直接用服务端的 `span`。证据接地时已经算好原文偏移，前端再搜一遍等于两份定位逻辑；
短证据和模糊匹配迟早不一致。代价是未接地的判定没有 `span`，只能显示"未定位"。

### 二、实现期问题

| 问题 | 现象与原因 | 处理 | 教训 |
| --- | --- | --- | --- |
| 测试断言确认框"消失"太脆 | Element Plus 的对话框关闭有过渡，jsdom 不跑完 transition，DOM 仍在；`wrapper.text()` 继续包含标题 | 去掉"关闭后文本消失"的断言，只断言"确认前没发请求、确认后发了什么" | 测行为，不测组件库的过渡细节 |
| 测试夹具的 `route` 被推断成 `string` | `DETAIL` 字面量的 `route: 'human'` 被拓宽，赋给 `ResultDetail` 时类型不兼容 | 夹具用 `as unknown as ResultDetail`；生产类型仍保持联合类型 | 测试夹具也要过类型检查，但别为了它放宽生产类型 |
| 队列页签切换需要重新取数 | `mode` 变了但 `load` 不会自己跑 | `watch([questionCode, mode])` 统一清选择、重新请求；请求序号丢弃过期响应 | 一个页面有多个筛选条件时，用一个 watch 管全部 |
| 自动通过结果在详情里显示"待复核" | 标题的状态只看“有没有复核记录”，没看 `route` | `route === 'auto'` 显示“待定稿”；`human` 才是“待复核” | 状态文案要按“下一步动作”命名，不是按来源 |
| 改分可以提交和原分一样的值 | `override` 记录会变成“改了但没改” | 页面要求分数有变化；分数没变时提示改用“采纳原分” | 两个按钮必须对应两种不同事实，不能都通向同一条记录 |
| 证据行和表格行点击冲突 | 勾选框点击会冒泡到行，打开详情 | 勾选框加 `@click.stop`；打开按钮也 `@click.stop` | 可选中的表格里，行点击是一个容易被误触的全局动作 |

### 三、自查与修正（本票未再起子代理）

| 问题 | 处理 |
| --- | --- |
| 批量通过入口不能出现在待复核页签 | 只在 `auto` 页签出现；服务端本来就只收 `route='auto'`，页面不制造整批 400 |
| 详情已定稿/已取代仍给表单 | `canReview = current && !review`；两种状态都只展示结论 |
| 改分意见只在服务端校验，页面会先发一次必败请求 | 页面先禁用按钮并给提示；服务端仍保留校验 |
| 高亮区间越界 | `answerParts` 校验 `start/end`，越界退回全文，不切出奇怪的片段 |
| 批量通过后队列不刷新 | 成功后清空选择并 `load()`；真实后端 `pending=true` 会把已定稿的排除 |
| 详情返回队列后不刷新 | 详情与队列是两条路由，返回时队列重新挂载并请求 |
| 自动通过详情没有“定稿”语义 | 标题改为“待定稿”，表单仍是采纳/改分 |
| 测试只覆盖成功路径 | 补了“取消批量通过”“没有意见不能改分”“已取代不能定稿”“已定稿只读” |

### 四、有意保留的判断

| 争议点 | 说明 |
| --- | --- |
| 批量通过只对自动结果 | 服务端规则；待人工复核必须逐份看证据，批量通过会绕过路由 |
| 改分必须写意见，采纳可不写 | 改分是人工覆盖模型结论；采纳是确认，意见可选 |
| 改分分数必须变化 | 避免“override 成原分”的假记录；想采纳就用另一个按钮 |
| 定稿后停留在详情页 | 让教师看到最终分与意见；回队列时自然刷新掉 |
| 队列不列已定稿历史 | 待办列表只放待办；历史入口留到需要时 |
| 风险排序不在前端重做 | 跨题不可比，服务端按题号分组后排序；前端重复排序会造出第二套顺序 |
| 高亮只显示当前点击的一处 | 多处同时高亮会互相覆盖、看不清；逐条点更接近“核对这一分”的动作 |
| 未接地的证据不能点 | 没有 span 就没有可靠位置；显示“未定位”比猜一个位置诚实 |
| 批量确认用页内对话框 | 可写清份数与后果，也比 `window.confirm` 可测 |
| 详情页不抽子组件 | 页面内部耦合在“一次结论”上，拆开只会增加 props/emits；队列与详情已经分路由 |

### 五、遗留

- 没有定稿历史页面；`GET /api/results?pending=false` 已支持，但没有入口。
- 队列只显示前 100 份（接口默认 `limit=100`），超过时提示“当前只显示前 N 份”，没有翻页。
- 批量通过只支持“全选当前页”，没有跨页选择。
- 详情页不显示每个采分点的全部等级定义，只显示中位等级、得分与证据；要看完整标准需回标准页。
- 证据高亮没有滚动到可视区的自动化验证；`scrollIntoView` 在 jsdom 里是空实现。
- 没有键盘操作与无障碍检查；证据按钮靠鼠标。
- 没有浏览器端到端测试；页面行为用 Vitest + jsdom 验证。

### 六、未决

- 定稿历史是否需要一个独立页面（按题号/日期筛选，显示最终分与意见）？
- 批量通过是否需要“跨页选择”或“按题号全选”？现在只是当前页。
- 改分是否需要“快捷扣分”（按采分点差额）而不是直接输最终分？
- “已被取代”的旧结论要不要允许查看当时的证据？现在只提示并给当前结论链接，详情本身仍可看。
- 队列的 `risk` 只在同题内可比；跨题查看时是否应该分组表头，还是强制先选题号？
