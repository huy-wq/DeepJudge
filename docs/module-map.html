Data Flow · Module Map

一次评分，数据到底怎么走

上半部分是参考项目 llmgrader 的真实链路（我逐文件读过），下半部分换成你要建的系统。 每个方框都标了数据在这一步的形态——XML、dict、提示词、JSON、pydantic 对象、数据库行，这是最容易糊涂的地方。

01llmgrader 的数据流（9 步）

从"讲师写 XML"到"学生看到分数"，中间只有一次模型调用；其余全是确定性的代码。

1
讲师写课程包（离线，一次性）
unit XML 里写题面、参考答案、采分点、分值、豁免说明。题面用 CDATA 包 HTML，公式用 LaTeX。
磁盘文件 · XML
2
unit_parser 加载并校验
用 xmlschema 按 unit.xsd 校验结构（元素名、必填项、枚举值），通过后解析成 Python 字典：question / parts / rubrics。
内存 · dict
3
学生在门户提交
选 unit + question，输入答案（可附图片）。浏览器带一个随机 session UUID，服务端不存身份信息。
HTTP · JSON + 图片
4
PromptBuilder 拼提示词
按「二值/部分给分 × 单部分/多部分 × 有/无 rubric」挑模板；把 rubric 逐条格式化成 - id / part / point_adjustment / display_text / condition / notes。
内存 · 纯文本提示词
5
调用模型
OpenAI Responses API，要求 text.format = json_object；模型支持时才传 temperature=0，不支持就整个不传。这里是全流程唯一的不确定环节。
网络 · HTTP 请求 / 响应
6
解析 + 宽松校验
先规范化（去代码围栏、去尾逗号），再用 GraderRawResult（pydantic）验证。策略是"宽进"：rubric_eval 里的杂项条目直接丢掉，不因一个小瑕疵废掉整份评分。
内存 · pydantic 对象
7
后端派生分数（关键）
grade_post_process() 算 max_points、逐部分 point_parts、聚合 result（全 pass→pass，全 fail→fail，含 error→error，其余 partial），并 clamp(0, max)。不计分的评语项强制清空分数。
内存 · GradeResult
8
落库
SQLite 一行：session UUID、unit/qtag、学生答案、参考解、rubric、结果、逐条证据、模型、时延、token 数。没有姓名学号。
磁盘 · SQLite 行
9
两个出口
网页：逐条展示"命中/未命中 + 证据"。Gradescope：导出 zip（run_autograder + results.json），那份 autograder 完全不调 LLM，只按存下的结果判分。
页面 / zip 包
看懂这条流的关键：模型只在第 5 步出现，产出的只是一段 JSON。 分数是第 7 步由普通 Python 算出来的——这就是"模型无权给总分"的实现形态，也是你该照搬的核心。

04这套 XML 涉及哪些标准

它没有自定义"新标准"，而是把几个现成标准叠起来用。

标准 / 技术用在哪要点
XML 1.0所有课程包文件文件头声明 <?xml version="1.0" encoding="UTF-8"?>
XSD 1.0schemas/ 下 6 个 schema：unit、unit_test、config、materials、skills、mcp_config用 Python 的 xmlschema 库校验；没有 targetNamespace（无命名空间，元素名全局唯一）；枚举值是写死的，如 condition_type 只能是 positive/negative
CDATA 段题面、参考答案、测试用例用来塞 HTML 而不转义 <；代价是内容里不能出现 ]]>
HTML 子集题面 / 解析渲染浏览器直接渲染 <p>、表格、图片
LaTeX + MathJax公式行内 \( \)、行间 \[ \]，由 CDN 加载的 MathJax 在浏览器排版（不在服务端渲染）
JSON模型输出、接口response_format / text.format = json_object，模型必须返回单个 JSON 对象
JSON Schema（pydantic 生成）模型输出校验extra="forbid" 拒绝多余字段；另有 Literal[...] 约束枚举
Gradescope Autograder 规范导出包run_autograder + results.json（/autograder/results/），支持签名校验
MCP（JSON-RPC 2.0）Course Builder让编辑器里的 agent 通过标准协议读写课程包
为什么用 XSD 而不是 JSON Schema？单一真源、IDE 有自动补全、schema 本身就是文档。 代价也很明显：CDATA 里套 HTML 很别扭，报错信息对非程序员不友好，版本演进时要做迁移脚本。 你的项目用 JSON + pydantic 更合适——你不需要给讲师提供 IDE 补全。

05换成 DeepJudge：同一条流，多三步

绿色是"和它一样"，蓝色是"你的系统多出来的"。多出来的三步，正是你的课题价值所在。

1
题目 + 采分点（JSON）
用 JSON 而非 XML，配 pydantic 校验：Σweight == total_score、id 唯一、等级合法。
JSON 文件
2
预处理
清洗、全半角/繁简规范化（保留原文用于证据定位）、脱敏、超长截断、注入文本检测。
内存 · 原文 + 规范化文本
3
拼提示词 + 调 Provider
与它相同：稳定前缀（题目+rubric+参考解）在前、答案在后；差异是这里走 GradingProvider 接口，供应商可换。
网络 · HTTP
4
多次采样（你的第一处增量）
同一输入跑 n=3，逐采分点取中位数，离散度算置信度。它不是"更准"，而是"知道自己有多不确定"。
内存 · n 份判定
5
证据接地校验（第二处增量）
它只信模型给的 evidence；你要拿 evidence 回原文做子串/LCS 定位，找不到标 UNGROUNDED、该点判 0 并转人工。
内存 · 带偏移的判定
6
服务端算分
与它相同：按 level→score 映射加权求和，模型无权给总分，clamp 到 [0, 满分]。
内存 · 聚合结果
7
校准 + 路由（第三处增量）
保序回归把刻度对齐教师；置信度低/边界分/接地失败 → 进人工复核队列。
内存 · 最终分 + route
8
落库 + 复核界面
与它相同：记录不含身份信息；差异是你需要"待复核队列"和证据高亮。
磁盘 · SQLite/PG
